# Subscriber Session

[criterion-session](../crates/criterion-session/src/lib.rs) owns the native Device Authorization transaction and in-memory subscriber credentials. Its fixed public registration and scope live in that module; [the provider contract](provider-contract.md) owns evidence for the native API and the separate website session. The public client identifier is not a secret. Authentication does not establish subscription entitlement, middleware admission or licensed playback.

The composed host SDL application has acquired a live production grant through first-party device activation and received issuer acknowledgment for one explicit revoke request, with local session/private-view disposal verified. This admits host linking and the logout request/lifecycle. [The account boundary](account.md) owns the admitted initial My List read in that journey. Live refresh/rotation, secure persistence and linking on the C4 remain separate requirements. The opt-in subscriber E2E uses only an external private activation capture; [current work](../TASKS.md) owns the remaining product admission.

`Session::with_transport` accepts an injected monotonic clock and transport. `HttpTransport::new` is the production fixed-origin HTTPS implementation; `SystemClock` supplies a monotonic epoch and can be cloned for UI scheduling. `start_link` returns the issuer's bounded user code, complete verification URI and expiry. The UI explicitly borrows these private strings for rendering. Verification URIs must use the exact issuer origin and `/activate` path, without credentials, nondefault ports or fragments; their query is bounded. No URI or code is logged or followed by this crate.

The owner calls `poll_once` at the returned deadline. Early calls return `WaitUntil` without a request. Pending uses the issuer interval; slow-down permanently adds five seconds. Network failures and issuer throttling/server errors back off exponentially, bounded at two minutes. Returned lifetime is measured conservatively from request start, and expiry is checked after awaited work. Device lifetimes, intervals, response sizes and attempt counts are capped in [the wire parser](../crates/criterion-session/src/wire.rs) and [session owner](../crates/criterion-session/src/session.rs); sample durations are never provider constants. Denial and expiry terminate the transaction. Malformed successful token responses require a new sign-in because the grant may already have been consumed.

`Session` serializes its in-memory requests. A rotated refresh token replaces the old token before another refresh or checkpoint can run; an absent or null optional refresh token preserves the current one. Transport failure, invalid response, expiry, cancellation or a dropped refresh future erase credentials and require sign-in, since remote rotation may have completed. No refresh is automatically replayed. Cancellation and disposal reject stale results. Logout erases local credentials immediately and attempts one revoke; overlapping or failed revoke returns `RevocationUnconfirmed` rather than claiming remote logout. The persistent lifecycle owner below separately keeps issued work alive when its public reply is dropped.

Logout acknowledgment is the issuer's admitted HTTP200 response, rather than an independent attempt to reuse the revoked token. Auth0's [revocation endpoint](https://auth0.com/docs/api/authentication/revoke-refresh-token/revoke-refresh-token) can revoke only that refresh token or the broader user/application/audience grant, depending on a tenant setting; Criterion's setting is unobserved. Neither local disposal nor that response establishes per-device isolation or the validity of another client's session. [Device reauthorization](https://auth0.com/docs/get-started/authentication-and-authorization-flow/device-authorization-flow) can wait until an existing access token expires. Do not replay a revoked refresh token or invoke account-wide logout to test these boundaries.

`with_access_token` borrows an unexpired token synchronously for the provider's header-construction seam. The callback must not block or re-enter the session. The provider owns its header role; this crate does not infer a bearer API. A callback panic poisons the state lock; the next state operation recovers it by erasing credentials. `dispose` also recovers and erases. Status distinguishes access refresh requirements, denied/expired linking, reauthentication and disposal.

## Persistence admission

The application remains volatile. No LG secure-storage backend or persistent production runtime integration is implemented or admitted. [SecureSessionStore](../crates/criterion-session/src/storage.rs) defines the platform boundary: authenticated encryption, exclusive restricted access, bounded serialized operations, atomic durable replacement/removal and fail-closed recovery from ambiguous storage completion. [PersistentSession](../crates/criterion-session/src/lifecycle.rs) implements conditional lifecycle ownership for an independently admitted backend. Platform integration must establish that backend's rights and recovery guarantees on the TV; there is no plaintext fallback or claimed keystore capability.

`Session::checkpoint` makes an explicit zeroizing refresh-token copy. Its versioned record binds the fixed issuer and client registration and excludes access tokens, device codes and activation instructions. `StoredSession::encode` produces private plaintext only for the admitted encryption seam; `decode` accepts a single bounded JSON object from authenticated/decrypted data and rejects changed version, binding, unknown fields or schema. `Session::restore` publishes no access token; a subsequent refresh must succeed before subscriber API use. The persistent owner performs both steps during startup restore.

`PersistentSession` owns both session and store behind one lifecycle mutex. Ordinary commands reject overlap. A retiring intent immediately denies new token borrowing and successful ordinary publication, then joins the issued operation before shutdown, logout or invalidation. Successful ordinary replies observe the current clock, session state and generation when consumed; held expired or superseded replies are rejected. Ordinary reply futures retain only weak ownership, so completed replies cannot keep session credentials alive after the public owner and issued jobs settle.

Startup `restore` confirms atomic `take`, including an absent record, before restoring or rotating a saved token. The checkpoint stays absent throughout the active session, including later refreshes. Only a successful, joined `graceful_stop` durably replaces the latest confirmed refresh checkpoint and disposes RAM credentials. `logout` and `invalidate` confirm removal; logout separately attempts issuer revocation. Credential or issuer uncertainty prevents saving a checkpoint. `StorageUnconfirmed` and `RevocationUnconfirmed` distinguish those failed confirmations without replaying a rotating request.

Issuance owns its job before returning the reply future; dropping that reply cannot cancel an issued storage or issuer operation. The injected runtime must stay alive until every issued job settles, including retirement waiting for lifecycle ownership. Public-owner `Drop` cannot await a disk barrier, save a checkpoint or certify removal. Application shutdown must join an explicit retirement before stopping the runtime; runtime abortion before a retirement job acquires ownership is unadmitted.

Every backend result must be settled, with no later mutation from that operation. An error or interrupted write must refuse ambiguous checkpoints on reopening until durable recovery establishes a safe state; an older interrupted write must never become eligible after a newer removal. The owner's in-memory failure latch cannot supply those guarantees. Controlled lifecycle tests establish consume/rotation ordering, stale publication, reply and owner lifetimes, shutdown and failure classification. Their fixture stores provide no at-rest protection or proof of TV durability.

## Transport and diagnostics

Production requests are form POSTs to fixed issuer device-code, token and revoke paths. The transport verifies TLS with static roots and the explicit pinned crypto provider, disables redirects, proxies, automatic retries and content decoding, and permits one active request per instance. Request and response bodies are bounded to 64 KiB; a ten-second total deadline includes body delivery, with a shorter connect deadline. JSON is required except the native revoke endpoint's empty HTTP200 response. Raw HTTP errors, headers, payloads and URLs never enter diagnostic errors.

Device-code, initial token, refresh and issuer-error DTOs require a single JSON object; positional arrays, scalar roots, duplicate known fields, wrong scalar field shapes and trailing non-whitespace data are rejected. Streaming map admission preserves the existing tolerance for unknown issuer extension fields and optional refresh-token omission/null without copying private text into an intermediate JSON value.

Secret text, private bodies, checkpoints and link instructions redact `Debug`/`Display`; application-owned buffers use zeroization. Bodies reserve their bound before collecting or encoding to avoid reallocating partial secrets. Explicit `expose` calls are capabilities whose callers must keep values private. TLS/HTTP internals and JSON/URL parser scratch can create temporary copies outside this erasure guarantee; zeroization is not a claim that every allocator or transport buffer is wiped.

Behavioral tests use controlled clocks and literal private fixtures; transport tests use a verified local TLS server with synthetic certificates. They cover timing, late/stale results, cancellation/disposal, malformed success, refresh rotation and uncertainty, persistence binding/recovery, redaction, certificate/hostname validation, redirect refusal, size limits and total deadlines. These establish local behavior, not production grant admission, subscriber entitlement, secure TV storage, DRM or TV playback.
